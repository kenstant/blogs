# 第 5 章 依赖倒置原则 · 里氏替换原则

> **原书位置**：《大话设计模式【Java溢彩加强版】》**第 5 章**（趣味篇名「会修电脑不会修收音机？」）  
> **类别**：**设计原则**（SOLID 之 **D**、**L**；不是 GoF 23 模式之一）  
> **痛点关键词**：高层直接 `new` 具体类、维修流程按设备类型写死、子类「能编译」却破坏父类语义  
> **一句话意图**：**模块都靠抽象耦合**；**任何 `IDevice` 实现都能交给同一套维修入口**，且替换后行为仍符合「能修」的约定。

## 零、原则原定义（简记）

- **DIP（依赖倒置）**：高层与低层**都依赖抽象**，不要高层直接绑死具体实现；「倒置」指依赖箭头从「自上而下压具体类」改为**共同依赖中间的接口**。  
- **LSP（里氏替换）**：子类型可以替换父类型/接口使用，且**程序语义仍正确**——能编译、能多态，不等于设计合格。  
- **与多态**：多态是机制；LSP 是**继承/实现是否靠谱**的约束。书外常提：正方形当矩形改宽高、企鹅当鸟却不能飞——**语法可替换，语义破坏**。

<details>
<summary>需要对照文献时的英文原句（可选）</summary>

**DIP（Robert C. Martin）**

> **A.** High level modules should not depend upon low level modules. Both should depend upon abstractions.  
> **B.** Abstractions should not depend upon details. Details should depend upon abstractions.

**LSP（可读版）**

> If \(S\) is a subtype of \(T\), then objects of type \(T\) may be replaced with objects of type \(S\) **without altering the desirable properties** of the program.

</details>

## 一、30 秒卡片（一眼回忆用）

- **它解决什么变化**：**具体设备、具体实现**在变；**维修流程**希望稳定。稳定侧是 **`IDevice`**；变化侧是 `Computer`、`Radio` 及未来 `Television` 的内部步骤。  
- **关键角色**：**高层**（`RepairService`、`Main`）只依赖 **`IDevice`**；**低层**各设备在 `repair()` 里实现自己的步骤。  
- **它和谁容易混**：与[第 4 章 OCP](./05-开放封闭原则.md)——OCP 问「新需求能否主要靠**加**代码接住」；DIP 问「依赖是否指向**抽象**」。与[第 2 章策略模式](./03-策略模式.md)代码形态也像，但 DIP/LSP 是**通用规则**，不限于某一模式名。

> 一个月后只看本节 + **第七节口诀** 即可回忆大半。

## 二、不用原则约束时怎么写（先看烂代码）

**需求（玩具）**：维修服务会修电脑，也会修收音机；以后可能加电视机。

**v1：按具体类型写死流程**

```java
// RepairServiceV1.java —— 高层「编排」每种设备的拆解顺序
public class RepairServiceV1 {
    void repairComputer(Computer c) {
        c.openCase();
        c.fixBoard();
        c.closeCase();
    }
    void repairRadio(Radio r) {
        r.openBack();
        r.fixCircuit();
        r.closeBack();
    }
}

// Computer.java —— 只暴露步骤，不负责「怎么串起来修」
public class Computer {
    void openCase() { /* ... */ }
    void fixBoard() { /* ... */ }
    void closeCase() { /* ... */ }
}

// Radio.java
public class Radio {
    void openBack() { /* ... */ }
    void fixCircuit() { /* ... */ }
    void closeBack() { /* ... */ }
}
```

（也有人把 `repairComputer` / `repairRadio` 写成 `repair(Computer)` / `repair(Radio)` **重载**，本质一样：都绑死在具体类型上。）

**v1 的痛点**：

- **高层知道太多细节**：`RepairService` 必须懂每种设备的拆解步骤，**加一种设备就加一个 `repairXxx(具体类型)` 方法**（或再多一个 `repair` 重载）。  
- **依赖方向不对**：业务入口依赖 `Computer` / `Radio` 等**低层具体类**，而不是稳定抽象。  
- **与 OCP 联动失败**：扩展新设备时，往往要**改** `RepairService`，而不只是**加**新类。

## 三、一步步演化

### 3.1 v2：抽象接口 + 细节各自实现

与 v1 对照时，重点看 **`RepairService` 是否还在编排具体步骤**，以及 **`Computer` / `Radio` 是否各自收口 `repair()`**。

```java
// IDevice.java —— 稳定抽象
public interface IDevice {
    void repair();
}

// Computer.java —— 步骤收进 repair()，对外只暴露契约
public class Computer implements IDevice {
    @Override
    public void repair() {
        openCase();
        fixBoard();
        closeCase();
    }
    // openCase / fixBoard / closeCase 私有实现略
}

// Radio.java
public class Radio implements IDevice {
    @Override
    public void repair() {
        openBack();
        fixCircuit();
        closeBack();
    }
    // openBack / fixCircuit / closeBack 私有实现略
}

// RepairServiceV2.java —— 高层只认 IDevice
public class RepairServiceV2 {
    public void repair(IDevice device) {
        device.repair();
    }
}

// Main.java —— 组装具体设备，不展开拆解步骤
public class Main {
    public static void main(String[] args) {
        RepairServiceV2 svc = new RepairServiceV2();
        svc.repair(new Computer());
        svc.repair(new Radio());
    }
}
```

**v1 → v2 一眼能看到的差别**：

| | v1 | v2 |
| --- | --- | --- |
| `RepairService` | 为每种设备写 `repairXxx`，**逐步调用** `openCase` / `openBack` … | 只有 `repair(IDevice)`，**不再知道**拆解顺序 |
| `Computer` / `Radio` | 提供零散步骤方法，**不会**自己 `repair()` | `implements IDevice`，在 **`repair()` 里串好**本设备流程 |

**好在哪 / 还差什么**：

- **DIP**：`RepairService` **只依赖 `IDevice`**；差异收进各设备 `repair()`，加新设备时**不必改**维修服务流程。  
- **LSP（在本例里）**：任意 `IDevice` 都可交给 `repair(IDevice)`；若某实现**少修一步或空实现**，调用方仍以为「修好了」——**编译通过 ≠ 可替换**（见第四节反例）。  
- **代价**：类与跳转变多，调试要追到具体实现才知道步骤。  

**与第 4 章 OCP**：新设备 ≈ **加** `implements IDevice` 的类；`RepairServiceV2.repair(IDevice)` 尽量**不因新设备而改**——OCP 是目标，DIP 是让依赖结构站得住的**手段**。

## 四、反例与代价

### 4.1 不必硬上 DIP

- 设备类型**长期只有一种**，也看不到第二种实现时间表——抽 `IDevice` + 多实现往往是 **YAGNI**。  
- 抽象契约还在**频繁推翻**，先稳定领域再谈倒置。

### 4.2 代价与 DIP 误用

- **类 / 文件变多**，阅读与调试要在接口与实现间跳转。  
- **契约要维护**：`repair()` 的语义、异常、前置条件要说清。  
- **误用**：永远只修一种 `Computer`，却维护 `IDevice` + 多个永不使用的实现——**抽象没换来扩展，只换来导航成本**。

```java
// 形似 DIP、难为扩展：接口只有一个实现，且永远不会有第二种
public interface IDevice { void repair(); }
public class OnlyComputer implements IDevice { /* ... */ }
```

### 4.3 LSP 违规（能编译，语义不对）

```java
// 仍 implements IDevice，但 repair() 空实现——svc.repair(device) 调用方以为修好了
public class BrokenRadio implements IDevice {
    @Override
    public void repair() {
        // 故意不修，或只 openBack 不 fixCircuit
    }
}
```

`RepairServiceV2` 无法从类型上区分「真修」与「假修」；这就是 LSP 要防的：**替换实现后，仍应满足「交给它的对象能被修好」这一约定**。

## 五、回到自己的代码

- **先闻味道**：打开一个业务 Service，看有没有一串 `repairXxx(具体类型)` / `handleFoo(FooClient)` / `saveByMysql(...)`——**方法名或参数类型已经写死实现种类**，且每加一种就要回来改这个类。这就是第二节 v1 在你项目里的样子。  
- **值不值得倒置**：第二种、第三种实现**已经在排期或线上跑着**，而 Service 还在复制流程 → 值得抽抽象 + `repair(接口)` 式入口；若**长期只有一种实现**、也看不到第二种，先别为「将来可能有」铺接口（见第四节 YAGNI）。  
- **LSP 单独看一眼**：搜 `implements` 你团队共用的那个接口，看有没有「空实现、只打日志、少调关键步骤仍当成功」的类——**编译能过，调用方语义却坏了**，比「没抽接口」更隐蔽。  
- **团队里常见的假 DIP**：几乎每个 Service 都配一个 `XxxService` 接口，仓库里却**常年只有一个 Impl**——可以挑一个模块问自己：**删掉接口后，哪一种已知的扩展会从「加实现类」变成「改 Service 里三处复制粘贴」？** 若想不到，这层更像习惯，不是 DIP 收益。  
- **和 OCP 一起想**：最近两次加需求，你是「**新加一个实现类 + 注册/注入**」为主，还是「**在老 Service 里再开一个 `repairTelevision`**」为主？后者偏多时，回头对照[第 4 章](./05-开放封闭原则.md)与第三节 v2。
